**产品的核心价值在于维护仍然有效的工作结论。**

例如“周五演示”“有人建议改周二”“负责人回复可以”“有人说自己周二来不了”，系统需要区分安排、提议、确认和个人状态，并且回答每个结论来自哪里。难点集中在事项归属、短回复的依赖关系、确认权限、时间变化及撤回后的状态。群报、追问和互动体验都依赖这些基础判断。

文档把首期范围收敛到查找、群报、状态跟踪和基本互动，并明确企业试点、真实模型、GPU 等尚未落实，能够帮助团队区分意图、实现和验证。不过“第一天接手”部分必须绑定正确的源码包，否则新成员会遇到入口、配置、数据格式和命令均不匹配的问题。负责人、仓库、分支、模型服务和验收联系人也仍待登记。

**上传代码的主要流程已经连通。**

`平台消息 → 原文存储 → 批量抽取候选操作 → 程序校验 → 事件记录 → 状态计算 → 事项与原文检索 → 回答校验或模板回退`

- 两套回放均显式使用 `--extractor gold --main-model ''`，即人工标注操作加模板回答，没有调用真实模型。
- 另写了 9 个小型复现检查，使用内存数据库与脚本化模型，全部复现下列行为。

12/12 的通过率证明现有固定样例能走通。评分函数主要检查答案是否包含或不包含某些字符串，并不系统核对每个结论、引用关系或遗漏。人工标注抽取还绕过了最困难的自然语言理解环节，不能据此推出真实群准确率、优于普通 RAG 或企业节时收益。

**需要优先处理的具体问题。**

| 问题 | 最小复现与实际结果 | 影响与修复方向 |
| --- | --- | --- |
| 回答可在没有证据时通过校验 | 给校验器输入“地点已经确定在火星基地，负责人是张三。”，claims=[]、cite=[]，结果为 accepted=true | 当前检查不验证地点、人物与正文是否由证据支持。优先约束事实字段的生成与呈现，并测试空 claims、错引、未引用断言和问题中的错误前提 |
| 撤回提议没有使其确认失效 | 初始八点；另一人提议九点；发起人引用回复“可以”；撤回九点提议后，状态仍为 confirmed、21:00 | 确认复制了提议取值，但 evidence 只保留“可以”，recall 不遍历 target_msg 的依赖。需要显式记录依赖并传播失效 |
| 删除事项后，新事件编号可能冲突 | 两个事项各有 E1、E2；删除第一个；更新第二个，触发 UNIQUE constraint failed: events.event_id | 事件编号取 COUNT(*)+1，删除后复用了仍存在的 E2。应使用数据库序列或不复用的唯一 ID |
| 忘掉事项没有清掉回答副本 | 先回答活动时间，再忘掉事项；answers 和 is_bot 消息里仍保留完整回答 | 删除不覆盖派生文字，之后导出的审核页仍可显示回答。需建立派生内容关联并清理相关日志、机器人消息、待确认记录等；已导出的静态文件需单独管理 |
| 跨平台群身份没有完整隔离 | 不同 platform、相同 group_id 与 msg_id 的第二条消息被判为重复 | 数据库主键、状态、配置和发送目标以裸 group_id 为主要键。应统一使用适配器实例与原生群 ID 构成的会话键 |
| 抽取输出格式错误会静默跳过 | 模型返回非 JSON，处理进度仍前进；pending 为空，再处理也不重试 | parse_ops 把解析失败当成空操作。需要区分正常无事件与抽取失败，记录可恢复的失败状态及有限重试 |
| 单次取消会取消整个周期事项 | 对固定周三活动输出 cancel、scope=instance、instance_expr=这周三，落库事件 scope 变为 item，整个系列状态为 cancelled | 取消分支没有保留单次作用范围。应对取消、完成和撤回同样维护 series/instance 边界 |
| 默认权限下可自荐成为有确认权的负责人 | 非发起人说“我负责”后再取消活动，状态成为 cancelled | 在 initiator_or_owner 规则下，participant/owner 直接赋予 owner 身份。需明确是否允许自荐获得拍板权；通常应把承担意愿与获授权负责人分开。designated 模式不依赖该 owner 判定 |
| 按称呼唤醒没有触发回答 | addressed=False 时发送“助手，现在怎么定的？”，得到空回复 | 名称判断只在适配层事后用于 stop_event，没有传入核心回应判断；可能同时抑制宿主默认回应。应在调用核心前统一计算 addressed |

**除此以外，产品闭环还有几项缺口。**

待确认区可以查看，但没有将记录确认、驳回并重新计算状态的用户操作入口；反馈会保存，但未自动修正事项。participation=active 的模型判断钩子没有在主流程接入，自然互动主要依赖回答提示与显式 @。查询会读取群历史并重新构造 BM25，后台也会读取全部事项与事件后计算状态，数据增长后的耗时与内存需要压测。这些属于现有实现边界，不能用文档中另一套实现的能力补足。

**推进顺序建议。**

1. 确认团队主线源码、版本与仓库，把文档的启动命令、配置、数据格式和测试数量绑定到这一版；另一份实现保留为明确标注的参考。
2. 将已复现问题转为正式回归案例，优先修复编号、证据依赖、事实校验、删除、群身份和失败恢复，明确负责人授权规则。
3. 在获准模型服务上用独立编写的自然对话测抽取和回答，分开记录事项归属、当前状态、来源支持、发言判断、延迟和总调用成本。
4. 实际验证一个测试群的普通消息、@、引用、撤回、重复推送和宿主回复接管，再演示查询与纠正闭环。
5. 用业务人员可评审的虚构场景展示收益与失败案例，取得具体合作方式、联系人和验收标准。训练选题应由上述评测暴露的瓶颈决定。
